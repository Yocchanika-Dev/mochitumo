## 1. 現時点の技術提案

次はBackend実装の初期案です。Phase開始時に変更可能です。

- SQLite書き込み競合は`BEGIN IMMEDIATE`と条件付き更新で制御する。
- 借り手ごとの進行中申請とbikeごとの成立済み申請を部分ユニーク制約で守る。
- NFC申請は`(device_id, client_request_id)`で冪等化する。
- ロックcommandは再送時も同じ`command_id`を使用する。
- commandは`queued / sent / acknowledged / succeeded / failed / timed_out`を区別する。
- 実シリアルとMock Serialを同じadapter interfaceにする。
- 既存v0.2 APIはすぐ削除せず、開発専用設定へ段階的に隔離する。
- IDはUUIDベース、時刻はUTC ISO 8601とする。
- SQLiteライブラリに`better-sqlite3`を使用する。
- NFC端末キーは端末ごとのsaltを使ったscrypt hashで保存する。

## 2. 本人確認・学生運用

合意が必要：

- 学生IDとLINE user IDを初回にどう安全に紐付けるか。
- 学校アカウント、対面確認、ワンタイムコード等のどれを使用できるか。
- NFCカードIDとstudent IDの登録者・管理場所。
- NFCカード紛失、再発行、無効化の運用。
- 休学・退学等で利用停止になった学生の同期方法。
- 表示名やstudent IDをLINEグループの他学生へどこまで公開するか。

禁止する設計：student IDを入力するだけでLINE連携、貸出申請、承認が成立すること。

## 3. 貸出業務

合意が必要：

- 借り手が申請を取消できる操作面（NFC、LINE、Web）。
- 一人が同時に持てる進行中申請数（提案は1件）。
- 一台の自転車が同時に対応できる貸出数（1件）。
- 承認後に機器故障した場合の管理者取消・復旧手順。
- 解錠成功後、何をもって返却・施錠成功とするか。
- 自転車の`maintenance`切替権限。
- LINE通知失敗時の利用者向け代替表示。

## 4. LINE連携

合意が必要：

- LINE Channelの管理者とChannel Secretの保管責任。
- WebhookをBackendが直接受けるか、LINE担当サービスが検証後に転送するか。
- 推奨はBackend入口でLINE公式署名を検証し、LINE担当がUXとMessaging API送信を担当する分担。
- MacBookを公開するHTTPSトンネルまたはリバースプロキシ。
- 学校ネットワーク規約上、外部公開が許可されるか。
- トンネルURL変更時のWebhook更新担当。
- LINEグループ内の通知先・個別返信・個人情報表示範囲。

## 5. NFC連携

合意が必要：

- NFC端末とBackend間でHTTPSを提供する方法。
- device keyの安全な発行、端末への書込み、交換、失効方法。
- UUID形式の`client_request_id`を端末再起動後も衝突させない生成・保存方法。
- 通信失敗時の最大再送回数と待機時間。
- カード登録・無効化・再発行を誰がどの管理画面または手順で行うか。
- NFC UID複製リスクを学校MVPとして許容できるか。
- HTTP検証に使う隔離ネットワークとダミー資格情報の管理。

## 6. USBシリアル・中継AtomS3

合意が必要：

- MacBook上の実デバイスポート名と選択方法。
- baud rate（暫定115200）。
- 1行最大長（暫定1024 bytes）。
- relay IDの発行・登録方法。
- ACK段階をrelay受信とbike受信の2種類にするか。
- ACKタイムアウト、実行結果タイムアウト、最大再送回数。
- MacBookまたはAtom再起動後の未完了command再送動作。
- 複数の中継Atomを将来扱う可能性。

## 7. ESP-NOW・自転車側AtomS3

ハード担当との合意が必要：

- 構造体の正確なフィールド、長さ、packing、エンディアン。
- protocol versionの更新方法。
- bike ID、source ID、target IDの表現。
- command IDをUUID 16 bytesで送れるか。
- result codeの一覧。
- sequenceの保存先と再起動時の扱い。
- 実行済みcommand IDを何件・どの程度の期間保存するか。
- ESP-NOW PMK/LMKの生成、書込み、交換、失効。
- CRCに加えて認証タグを使用するか。
- サーボが実際に解錠・施錠したことを検出するセンサー。
- LED、サーボ、ロック異常時の具体的な結果コード。

## 8. 運用・セキュリティ

合意が必要：

- MacBookを常時起動する担当とスリープ防止設定。
- SQLite DBのバックアップと個人情報保持期間。
- ログの閲覧権限と保存期間。
- `.env`や機器鍵の安全な共有方法。
- デモ環境と本番相当環境の分離。
- 事故時の自転車手動解錠・施錠手順。
- 認証なしの既存v0.2 APIを無効化する時期。

## 9. Phase 2で確定済み・未確定の事項

確定・実装済み：

1. SQLiteは`better-sqlite3`を使用する。
2. 開発seedは`S1001`、`S1002`、`B003`を使用する。
3. 二重申請は借り手1人につき進行中1件とする。
4. 既存v0.2 APIを当面維持する。
5. NFC端末はdevice ID/keyで認証し、Mockも同じ実APIを利用する。
6. `card_uid`はFeliCa IDmとし、Backendで大文字16桁へ正規化する。

未確定：

1. 本番device keyの発行・ローテーション・失効手順。
2. カード管理の責任者と管理用インターフェース。
3. 学内環境で利用するHTTPS終端方法。
4. NFC UID複製リスクへの追加対策。
